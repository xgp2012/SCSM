## V0-1 — PTY 彩色终端验证（D1 核心）

**来源**：计划 §10 表格；§5.2（彩色链路）；§5.3（指令通道）；§A.8（承认未验证）

### 假设

> 在 PTY 下启动服务端，日志出现 `EnhancedTerminalLogSink initialized With ANSI Support`
> （**而非** `输出被重定向，使用基础终端模式`）；
> 通过 PTY 发送 `help` 能收到**带 ANSI 色**的 `[help]: ...` 回复；
> 且**终端来源被识别为 true**，从而使指令免于权限校验。

### 精确测试步骤

> 待补齐实际路径后执行。以下为**步骤框架**。

1. **确认前置**：`which dotnet` 有输出；`template_dir` 指向已解压的服务端；
   `python3 -c 'import pty; pty.openpty()'` **成功**（否则本任务无意义）。
2. **基线（管道模式）**：以 `sh -c '<server> | cat'` 启动，记录首行终端模式日志文案。
   → 期望：`输出被重定向，使用基础终端模式`。
3. **PTY 模式**：用 `creack/pty` 分配 PTY，`TERM=xterm-256color` 启动服务端，
   捕获全部输出到文件（保留原始字节，**不要**经过任何剥离 ANSI 的处理）。
4. **断言 A（终端模式）**：输出包含 `EnhancedTerminalLogSink initialized With ANSI Support`，
   且**不**包含 `输出被重定向`。记录**两种首行原文样本**。
5. **断言 B（ANSI 存在）**：原始输出中 `\x1b[` 出现次数 > 0。记录**原始 ANSI 字节样本**（十六进制）。
6. **断言 C（指令通道）**：向 PTY 主端写入 `help\n`，读取从端输出，
   确认收到 `[help]: ...`，且**带 ANSI 色**。
7. **断言 D（终端来源 / 权限）**：确认 `isTerminal` 是否被置位——
   尝试一条**需要权限**的指令（如 `/player list 0`），观察是否被权限校验拒绝。
8. **断言 E（TERM 取值）**：对比 `TERM=xterm-256color` 与 `TERM=dumb`/未设置时的输出差异。
9. **断言 F（去回显）**：确认 PTY 是否需要关闭 `ECHO`（否则指令会被回显污染日志）。
10. **断言 G（容器内）**：在 Docker 中重复 3–9，分别测试 `--tty` 与不带 `--tty`。
    → **与 V0-3 联测。**

### 验收标准

| 断言 | 通过条件 |
|---|---|
| A | 出现增强终端日志文案；**两种模式的首行样本均已记录** |
| B | 原始输出含 `\x1b[`；**ANSI 原文样本已附** |
| C | `help` 有回复且**带色** |
| D | 明确回答"指令是否需要权限"，并给出证据 |
| E | 记录 `TERM` 的最优取值及依据 |
| F | 明确回答"是否需去回显" |
| G | **容器内同样通过**（`--tty` 或已确认的具体参数） |

## V0-2 — 停止行为验证

**来源**：计划 §10；§5.4（停止与保存策略）

### 假设

> 在 PTY 下，`Ctrl+C`（`\x03`）、`/stop` 指令、`SIGTERM`、`SIGKILL` 四种方式中，
> **至少有一种**能保证服务端**优雅停机且存档落盘**。

### 精确测试步骤

1. 启动一个实例、创建/修改世界（使内存状态与磁盘状态**可区分**）。
2. **方式一 `\x03`**：向 PTY 写 `\x03`，观察退出码、退出日志、存档 mtime 变化。
3. **方式二 `/stop`**：向 PTY 写 `/stop\n`。
   ⚠️ 注意计划已记录：`Server/EssentialCmd/CmdStop.cs` 的 `ProcessCmd()` 是**空实现**——
   预期此方式**可能无效**，需实测确认。
4. **方式三 `SIGTERM`**：向进程（及**进程组**）发 `SIGTERM`。
5. **方式四 `SIGKILL`**：发 `SIGKILL`（对照组——预期**丢失**未落盘改动）。
6. 每种方式后：`ls -la --time-style=full-iso` 存档与 `.bak` 的 mtime；
   重启并确认世界状态是否为最后修改的状态。

### 验收标准

- 明确**哪种方式**能保证存档落盘（或明确"都不行"）
- 记录**每种方式的退出码与退出日志**
- 产出**停止 SOP**（写回计划 §5.4）
- 确认面板应使用的停止序列（含超时与升级到 SIGKILL 的阈值）

### 当前状态

🟡 **部分执行**。已对真实服务端执行过一次停止并取得退出码；四种方式的**逐一对比**与
**存档 mtime 判定**尚未完成。

### 结果

```text
【部分执行 — 依据计划附录 D.4，2026-10-06】

实测返回值：
  {"instance_id":1,"forced":true,"exited":true,"exit_code":143,
   "duration_ms":30132,"state":"Stopped"}

方式一 \x03    ：在 30s 预算内**未**终止进程 → 无效
方式二 /stop   ：在 30s 预算内**未**终止进程 → 无效
                 （与计划预判一致：CmdStop.ProcessCmd() 是空实现）
方式三 SIGTERM ：有效。退出码 143（=128+15），耗时 30132ms
方式四 SIGKILL ：未测（未执行；对照组）
停止 SOP：优雅路径（/stop + Ctrl+C）→ 超时 30s → SIGTERM → 退出（rc=143）
         即：**当前实际生效的停止手段只有 SIGTERM**

存档 mtime 证据 —— **相互矛盾，未定论**：
  记录甲（附录 D.4）：停止后 Worlds/World/Project.json mtime(12:53)
                       **晚于** Project.json.bak(12:52) → 支持"存档已落盘"
  记录乙（另一轮观测）：PROJ advanced: NO / BAK advanced: NO → 支持"存档未落盘"
  两者不可同时为真，需以"可区分内存态与磁盘态"的世界改动重测（见测试步骤 1）。

结论：**"哪种方式能保证优雅停机"已回答一半 —— 只有 SIGTERM 能在预算内终止进程。**
  1. 优雅路径（`/stop` 指令 + Ctrl+C）**双双失效**，迫使梯子升级到 SIGTERM
     —— 实测印证了计划把 `CmdStop.ProcessCmd()` 空实现列为**高风险**的判断（A 级证据）。
  2. 退出码 143 说明进程**收到并响应**了 SIGTERM（非 SIGKILL 的 137），
     即运行时确实存在正常的信号处理路径。
  3. **存档是否落盘（本项的核心验收标准）仍未定论**：两条反向观测相互矛盾，
     不得据此宣称"SIGTERM 保证存档安全"，也不得宣称"会丢档"。
     §6.5「启动前强制备份」策略**应继续保留**——它不依赖本结论。
遗留问题：
  - 存档落盘矛盾需一次干净的重测（先做可区分的世界改动，再分别测四种方式）。
  - `/stop` 失效的根因待确认：是空实现（读码结论），还是需要参数（如 `/player list 0`）。
  - FIFO 通道（`command-fifo`）与 `--enhanced` 是否可替代 PTY 指令通道，未验证。
  - SIGKILL 对照组未测，无法给出"丢失量"上界。
```

## V0-3 — 运行时与部署验证（含容器内 PTY）

**来源**：计划 §10；§9.1（裸机）；§9.2（Docker）

### 假设

> 干净 Linux 上**仅装 .NET runtime** 后，`start.sh` 路径可跑通；
> **Docker 容器内 PTY 可用**（`--tty`，或需特定 `docker run` 参数）。

### 精确测试步骤

**裸机部分：**
1. 在干净 Linux（或容器）上仅安装 .NET runtime（不含 SDK）：`./scripts/install-dotnet.sh`。
2. 验证 `dotnet --list-runtimes` 含 `Microsoft.NETCore.App 10.x`。
3. 解压服务端发行物，执行 `start.sh`，确认能进入监听状态。
4. 确认**不需要** `Microsoft.WindowsDesktop.App`（它是客户端专属框架）。

**容器部分（对应 D1）：**
5. `docker build -f deployments/Dockerfile -t scnetm:dev .`
6. **不带 `--tty`** 运行，容器内执行 PTY 探测：
   `docker run --rm scnetm:dev python3 -c 'import pty; pty.openpty()'`
   （镜像若无 python，改用 `sh -c 'test -w /dev/ptmx && echo writable'` 或自备探针）。
7. **带 `--tty`** 重复步骤 6。
8. 对比步骤 6/7，确定 **`--tty` 是否必要/充分**。
9. 验证 `docker compose config` 通过；按 compose 起服务，确认面板 `/healthz` 可达。
10. 确认容器内**面板能创建进程组**（停止实例时整个进程组一起退出，无孤儿）。

| 断言 | 通过条件 |

| 裸机 | 仅 .NET runtime 即可跑通 `start.sh` |

| 参数固化 | 所需参数**已写入 `deployments/docker-compose.yml`** |

### 仍被阻塞

| 项 | 阻塞原因 | 可否本机解除 |
|---|---|---|
| V0-1 PTY 彩色 | `/dev/ptmx` → EACCES 13（设备类级） | ❌ |
| V0-2/7 指令通道相关 | 同上（与彩色共用前提） | ❌ |
| V0-3 容器部分 | Docker daemon 不可访问 | ❌（需加 `docker` 组） |

> **一句话**：**PTY 是唯一未解除的硬阻塞**，它同时挡住彩色显示与指令通道；
> 而 `--tty`/容器内 PTY（V0-3）是**另一个**独立的 Docker 侧阻塞，两者不可混为一谈。
