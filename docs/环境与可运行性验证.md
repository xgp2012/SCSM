## 3. PTY 问题（D1 的关键）—— 本报告的核心

计划决策 **D1**（仿真终端保色）以及任务 **V0-1/V0-3** 全部依赖 PTY 可用性。
计划 §A.8 明确承认**该路径从未被运行时验证**。本节正面处理它。

### 3.1 三个独立角度的一致失败【实测】

**角度一：Python `pty.openpty()`**

```text
$ python3 -c "import pty; print(pty.openpty())"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File "/usr/lib/python3.10/pty.py", line 34, in openpty
    master_fd, slave_name = _open_terminal()
  File "/usr/lib/python3.10/pty.py", line 64, in _open_terminal
    raise OSError('out of pty devices')
OSError: out of pty devices
```

> **陷阱提示**：这里的文案 **"out of pty devices" 是误导性的**。它是 Python 标准库对
> `openpty()` 失败的**固定文案**（`pty.py` 中硬编码），**并不代表真的"PTY 耗尽"**。
> 见 §3.3 —— 实际 errno 是 **13 `EACCES`（权限拒绝）**，且 PTY 余量充足（4/4096）。
> 我在 `verify-env.sh` 中特意把 errno 一并打印出来，以避免这个文案误导后续读者。

**角度二：`script(1)` 命令**

```text
$ script -qc 'echo hello' /dev/null
script: failed to create pseudo-terminal: Permission denied
$ echo $?
1
```

→ 与 Python **同样的失败**，但错误文案是准确的 `Permission denied`。

**角度三：Go `github.com/creack/pty`（生产代码将要使用的库）**

在 `/tmp/ptyprobe` 建独立模块（`module ptyprobe`，含 `github.com/creack/pty v1.1.24`），
**不干扰主模块**：

```text

  FAIL: open /dev/ptmx: permission denied | errno=13 (permission denied)
== raw os.Open on /dev/ptmx ==
  O_RDONLY             OK /dev/ptmx
  O_WRONLY             FAIL open /dev/ptmx: permission denied | errno=13 (permission denied)
  O_RDWR               FAIL open /dev/ptmx: permission denied | errno=13 (permission denied)
  O_RDWR|O_NOCTTY      FAIL open /dev/ptmx: permission denied | errno=13 (permission denied)
  O_RDWR|O_NONBLOCK    FAIL open /dev/ptmx: permission denied | errno=13 (permission denied)

  isatty(stdin): false  isatty(stdout): false
```

**三个角度全部失败，errno 一致为 13。** `creack/pty` 的 `pty.Open()` 在**第一步就失败**。

### 3.2 失败发生在哪一步？—— 精确到系统调用【实测】

PTY 分配的完整路径是：

1. `fd = open("/dev/ptmx", O_RDWR)` ← **在这里失败**
2. `ioctl(fd, TIOCGPTN, &n)` 取从端编号
3. `grantpt(fd)` / `unlockpt(fd)`
4. `open("/dev/pts/N", O_RDWR)` 打开从端

| 步骤 | 实测结果 |
|---|---|
| **1. `open("/dev/ptmx", O_RDWR)`** | **FAIL，errno 13 `EACCES`** ← **失败点** |
| `open("/dev/ptmx", O_RDONLY)` | **OK**（成功！） |
| `open("/dev/ptmx", O_WRONLY)` | FAIL，errno 13 |
| 2. `ioctl TIOCGPTN` | **未到达**（fd 无法获得） |
| 3. `grantpt`/`unlockpt` | **未到达** |
| 4. `open("/dev/pts/N", O_RDWR)` | 亦失败：`open("/dev/pts/0", O_WRONLY)` → errno 13 |

**关键发现：不是 `grantpt`/`unlockpt` 失败，也不是 `/dev/pts/N` 失败——
而是最外层的 `open("/dev/ptmx", O_RDWR)` 就被拒绝了。**

`strace` 佐证（`strace` 可用）：

```text
$ strace -f -e trace=openat,open,ioctl python3 -c "import os; os.open('/dev/ptmx', os.O_RDWR)"
openat(AT_FDCWD, "/dev/ptmx", O_RDWR|O_CLOEXEC) = -1 EACCES (Permission denied)
```

### 3.3 排除各类常规原因【实测】

| 假设原因 | 排查结果 | 判定 |
|---|---|---|
| **PTY 耗尽** | `/proc/sys/kernel/pty/nr` = **4**，`max` = **4096** | ❌ **排除**（余量 99.9%） |
| **权限位（DAC）问题** | `/dev/ptmx` 是 `crw-rw-rw-`（0666）；`os.access(W_OK)` 返回 **True** | ❌ **排除**（DAC 允许写） |
| **用户不在 `tty` 组** | 用户确实不在 `tty` 组，但 `/dev/ptmx` 是 0666，**不需要**该组 | ❌ **排除**（无关因素） |
| **`devpts` 未挂载** | 已挂载：`devpts rw,nosuid,noexec,relatime,gid=5,mode=620,ptmxmode=000` | ❌ **排除** |
| **`ptmxmode=000` 配置错误** | 这是 **Linux 标准默认值**；正确用法是用 `/dev/ptmx` | ❌ **排除**（配置正常） |
| **seccomp 拦截** | `/proc/self/status` → `Seccomp: 0`，`Seccomp_filters: 0` | ❌ **排除**（完全未启用） |
| **AppArmor 限制** | `/proc/self/attr/current` → `unconfined` | ❌ **排除** |
| **缺 capability** | `CapEff: 0000000000000000`（空），`CapBnd: 000001ffffffffff` | ⚠️ 常规——打开 0666 设备**不需要** capability |
| **`NoNewPrivs=1`** | 已设置，导致 `sudo` 无法提权 | ⚠️ 它阻止了"换用户重试"这条路（见 §3.5） |

**所有常规原因全部排除。** 那么限制来自哪里？

### 3.4 决定性证据：限制是「设备级」而非「PTY 专用」的【实测】

我系统性测试了 `/dev` 下多个字符设备，结果呈现出**极强的规律性**：

| 设备 | `O_RDONLY` | `O_WRONLY` | `O_RDWR` |
|---|---|---|---|
| `/dev/null` | OK | **OK** | **OK** |
| `/dev/zero` | OK | **errno 13** | **errno 13** |
| `/dev/full` | OK | **errno 13** | **errno 13** |
| `/dev/random` | OK | — | **errno 13** |
| `/dev/urandom` | OK | — | **errno 13** |
| `/dev/tty` | errno 6 | — | **errno 13** |
| `/dev/console` | **errno 13** | — | **errno 13** |
| `/dev/tty0` / `/dev/tty1` | — | **errno 13** | — |
| `/dev/pts/0` / `/dev/pts/4` | — | **errno 13** | — |
| **`/dev/ptmx`** | **OK** | **errno 13** | **errno 13** |

**这个模式是决定性的：**

1. **读打开几乎处处成功**，写打开几乎处处失败。
2. **唯一例外是 `/dev/null`**——只有它是读写均可的。
3. `/dev/zero` 与 `/dev/null` 的 **DAC 权限完全相同**（都是 `crw-rw-rw-`）、
   **rdev 同类**（1:5 vs 1:3）、**同一个 `/dev` tmpfs 挂载**。
   任何基于**权限位 / 设备主次号类 / 挂载选项**的策略都**无法区分**二者。
4. → 因此这是一个**按设备节点（inode/名称）白名单**的策略：
   **`/dev/null` 被放行，其余设备的写打开被一律拒绝。**
5. → **PTY 不是被专门针对的**；`/dev/ptmx` 只是"非 `/dev/null` 设备"中的一员。

**旁证：该限制会被子进程继承【实测】**

```text
$ sh -c 'python3 -c "import pty; pty.openpty()"'   → OSError: out of pty devices
$ env -i /usr/bin/python3 -c "import pty; pty.openpty()"  → OSError: out of pty devices
```

即使清空环境变量（`env -i`）仍然失败 → **限制在进程创建时被继承**，不是环境变量造成的。

**旁证：harness 自报存在 Landlock 沙箱【实测】**

```
landlock-run: partial enforcement (older Landlock ABI)
```

**这条消息在我执行的每一条 bash 命令的 stderr 上都出现。** 它明确说明：
DSH harness 用一个名为 `landlock-run` 的组件对本会话施加了 **Landlock** 沙箱，
且因内核 ABI 较老而只能"部分执行"。

### 3.5 是沙箱假象还是真实主机限制？—— **无法决定性证明**，但强指向沙箱

**这是本报告最需要诚实的地方。我必须明确说明：我无法在此环境中做出决定性判定。**

**指向「沙箱假象」的证据（支持 D1 在真实目标上可行）：**

1. **【实测】限制是设备类级别的，不是 PTY 专用的。** 一个"针对 PTY 的宿主限制"在技术上
   毫无道理——`/dev/ptmx` 是 0666，PTY 余量 4096 中的 4。真实 Linux 上没有这样的默认策略。
2. **【实测】`/dev/null` 被单独放行。** 这是**沙箱白名单**的典型特征：
   沙箱作者需要放行 `/dev/null`（否则几乎所有程序都会报错崩溃），
   但无暇/无意放行其他设备。真实内核策略不会这样"只放 `null`"。
3. **【实测】harness 明确自报 Landlock 沙箱**（`landlock-run: partial enforcement`）。
4. **【实测】限制被 fork/exec 继承**，符合进程级 LSM/策略继承的特征。
5. **【实测】本机是 KVM VM 而非容器** → 不存在容器 device cgroup 对 VM 内进程施加策略的可能，
   于是"谁在限制我"的候选者只剩：内核 LSM 或宿主注入的用户态监管器。

**指向「真实限制」的证据 / 未能排除的疑点：**

1. **【实测】Landlock ABI 版本是 1。** `landlock_create_ruleset(NULL, 0, VERSION)` 返回 **1**。
   而 **Landlock ABI 1–3 只能限制文件系统访问**；设备访问控制（`IOCTL_DEV`）
   **最早出现在 ABI 4（内核 6.10+）**。本机内核 **5.15**，ABI=1。
   → **从 Landlock 的语义上讲，它根本不应该能拒绝一次 `open()`。**
   这就是为什么我**不能**简单地把原因归给"Landlock"。
2. **【实测】seccomp 关闭（`Seccomp: 0`）、AppArmor `unconfined`。**
   常规的三条 LSM/过滤路径看起来都不成立。
3. **因此存在一个我未能解释的缺口**：一个非 Landlock（或 Landlock 之外）的机制
   在以设备节点为粒度拒绝写打开。

> **诚实结论：机制的精确归属我无法确定。** 我实测到的确定事实是：
> **限制存在、粒度是设备节点、`/dev/null` 例外、被继承、且 harness 自报 Sandbox。**
> 我**推断**（中等偏高置信度）这是 harness 沙箱的产物，而非目标主机的固有属性；
> 但**我不能证明这一点**，因为内核 LSM 的实际规则集对一个非特权进程**不可读**
> （`/sys/kernel/security/landlock/` 不存在；`capability` LSM 生效但规则不可枚举）。
>
> **能决定性判定它的证据（本环境无法获取，需在宿主/特权侧执行）：**
> - 以**同一用户**在**沙箱外**（另开一个非 DSH 的 SSH/serial 会话）执行
>   `python3 -c 'import pty; pty.openpty()'`。
>   若成功 → **沙箱假象**（D1 在目标上可行）。
> - 检查 harness 进程的完整命令行与 seccomp/Landlock 规则：
>   `cat /proc/<landlock-run-pid>/status`、`ls -l /proc/<pid>/fd`、以及宿主侧的审计日志。
> - 用 `bpftrace`/`perf` 跟踪该 `openat` 的 `-EACCES` 返回路径
>   （需要 `CAP_BPF`/`CAP_SYS_ADMIN`，本机 `CapEff` 为空，**不可用**）。
> - 在**另一台 Linux 主机**上重复同一测试。

- 在 pnpm 10+ 中，未批准的依赖构建脚本可能使 `pnpm install` **以非零码退出**并报

- `User=scnetm` 专用非特权用户 + `WorkingDirectory=/srv/scnetm`（实例 CWD）。
- 头部注释明确解释「面板必须能创建进程组与 PTY」的原因。
